    Authentication standard

    How authentication works in all software developed by the Societal Analytics Lab (AmCAT, AnnoTinder): what the software does, and what it requires from the OIDC provider. It is written for developers of our software. Teams that host the software only need parts of it; these pages link to those:

    • Authentication provider: for teams that host our software.
    • Migration guide: moving to a different OIDC provider.
    • Decisions: why it is set up this way, and which alternatives we dropped.

    OpenID Connect (OIDC)

    OIDC is an open standard for authentication that builds on top of the OAuth 2.0 protocol. It allows clients to verify the identity of users based on the authentication performed by an external identity provider (IdP). By using OIDC, our software does not handle user authentication directly, but delegates it to an external OIDC provider. This is an industry standard, because it outsources the hard part of authentication to a dedicated provider, which is often better equipped to handle it than the application itself.

    Our software works with any OIDC provider that meets the provider requirements. The person hosting our software chooses the provider, and is responsible for making sure it is suitable. The safest choice is a provider that is managed by a security team and has a helpdesk for account recovery. Talk to your institution's IT support circle.

    Choosing an OIDC provider

    The person hosting our software chooses the OIDC provider (see Authentication provider):

    • Your institution's identity provider (recommended, and the right choice for sensitive research data): managed by a security team, with a helpdesk for account recovery.
    • Another provider that meets the requirements, hosted (e.g. ZITADEL Cloud) or self-hosted (e.g. Keycloak). The lab runs its own Keycloak for its own servers; its documentation (Keycloak) can serve as an example.
    • For teaching and other servers without sensitive data: a provider that doesn't meet all requirements, with the weaker security settings turned on.

    Names and email addresses of users (e.g. students) are personal data, so any server must be used according to your institution's rules. Moving to another provider is a migration. For development on a local machine there is a separate development mode.

    OIDC provider requirements

    By default, the provider must meet all three requirements. The first two can be turned off, for teaching and other servers without sensitive data (see Weaker security).

    Requirement What the provider must do
    Email verification Return "email_verified": true in the ID token. Our software uses email addresses to assign roles (see Authorization).
    2FA with a usable signal Support 2FA, and signal in the ID token that it was used. Providers do this differently (amr containing mfa, or a specific acr value), so the claim is configured with OIDC_MFA_CLAIM. See Provider support for MFA signals.
    Step-up Honour the max_age parameter (re-authenticate if the last login is older than N seconds), and return auth_time in the ID token. This one can't be turned off.

    Configuration

    Proposed names; to be aligned with the AmCAT and AnnoTinder code.

    Variable Required Description
    OIDC_HOST yes Issuer URL of the trusted OIDC provider.
    OIDC_CLIENT_ID yes Client ID registered at the provider.
    OIDC_CLIENT_SECRET yes Client secret registered at the provider.
    OIDC_MFA_CLAIM no Which claim counts as 2FA: amr:mfa (default) or acr:<value>, e.g. acr:http://test.surfconext.nl/assurance/loa2 for SURFconext.
    AUTH_SESSION_IDLE, AUTH_SESSION_MAX no The application's own session: seconds without activity, and seconds in total, before the user signs in again (see Sessions and signing out). Default: 1800 and 86400 (30 minutes, 24 hours).
    AUTH_STEP_UP_MAX_AGE, AUTH_STEP_UP_IDLE no Sensitive actions: the maximum age in seconds of the last 2FA login, and the seconds since that login or the last sensitive action (see Two-factor authentication). Default: 3600 and 900 (1 hour, 15 minutes).
    OIDC_PREVIOUS_HOST, OIDC_PREVIOUS_CLIENT_ID, OIDC_PREVIOUS_CLIENT_SECRET, OIDC_PREVIOUS_MFA_CLAIM no The previous OIDC provider, only during a migration.
    OIDC_PREVIOUS_UNTIL no Date after which the previous provider is no longer accepted.
    AUTH_DEV_MODE no Enables development mode. Refused unless the server only listens on localhost.
    AUTH_INSECURE_DISABLE_2FA no true turns off the 2FA requirement (see Weaker security).
    AUTH_INSECURE_DISABLE_EMAIL_VERIFICATION no true turns off the email verification requirement (see Weaker security).

    Two-factor authentication (2FA)

    For sensitive actions (e.g. creating API keys, changing roles) our servers require a recent 2FA login (step-up authentication), in a window like GitHub's "sudo mode": the login is at most AUTH_STEP_UP_MAX_AGE old (1 hour), and at most AUTH_STEP_UP_IDLE (15 minutes) has passed since that login or the last sensitive action. Each sensitive action renews that 15 minutes, so a batch of admin work needs one login, not one per change. (OWASP's verification standard requires a recent login or re-authentication before sensitive actions, without prescribing a window; 15 minutes is OWASP's idle timeout for high-value applications, at the strict end.)

    1. The server checks OIDC_MFA_CLAIM and auth_time in the ID token of the session's login, and when the last sensitive action was.
    2. If the claim is missing or the window has passed, the server sends the user to the OIDC provider for a new login, with max_age=0 and prompt=login (Keycloak skips max_age=0 when the last login was within the same second; prompt=login always asks).
    3. The server checks the new ID token itself, because providers do not always enforce what was requested.

    With AUTH_INSECURE_DISABLE_2FA, steps 1 to 3 only check auth_time: sensitive actions still need a recent login, but not a second factor.

    Account recovery (e.g. a lost phone) is the responsibility of the OIDC provider.

    Weaker security: teaching and low-sensitivity servers

    Two requirements can be turned off, each with its own setting. Both are deliberately named INSECURE: they make the server less secure, and must never be used for servers with sensitive research data. In .env:

    # Weaker security: only for teaching and other servers without sensitive data.
# See https://vu-societal-analytics.github.io/societal-analytics-lab-infra/auth/#weaker-security-teaching-and-low-sensitivity-servers
AUTH_INSECURE_DISABLE_2FA=true
AUTH_INSECURE_DISABLE_EMAIL_VERIFICATION=true

    AUTH_INSECURE_DISABLE_2FA=true

    • Sensitive actions (e.g. creating API keys, changing roles) no longer require a second factor, but still require a recent login (step-up with max_age and auth_time).
    • The server still records whether a login used 2FA (has_mfa, with OIDC_MFA_CLAIM), so admins can see who uses it anyway.
    • Risk: anyone who gets hold of a user's password, or their email (to reset it), can perform that user's sensitive actions.

    AUTH_INSECURE_DISABLE_EMAIL_VERIFICATION=true

    • Users can log in when the provider doesn't confirm their email address (email_verified is false or missing). The server records what the provider sent (email_verified in the user table).
    • Roles given to an email address (invitations, see JIT account claiming) can still be claimed by a user whose address is not verified. That is the risk: on a provider where people can choose their own address, someone could claim the roles meant for someone else. Only use this setting with a provider that does verify addresses but doesn't send the claim (e.g. some institutional providers).
    • Roles based on the email domain, or on having a verified address (ABAC, require_email), still only apply to users with email_verified = true.

    Both settings:

    • The server logs a warning at every start.
    • The admin page permanently shows them as hardening warnings.
    • Turning a setting off again restores the requirement: users who don't meet it can no longer log in (email) or perform sensitive actions (2FA).

    API keys

    Our software also supports direct API access via API keys. These are application-managed tokens that are decoupled from the OIDC provider.

    • API keys can only be created and changed by the main web client, in a session that passed step-up authentication.
    • API keys always have a limited scope.

    Server hardening warnings

    The web client shows server admins a list of warnings for things that make the server less secure:

    Warning Meaning
    2FA not required AUTH_INSECURE_DISABLE_2FA is set: sensitive actions don't need a second factor. Not for sensitive data (see Weaker security).
    Email verification not required AUTH_INSECURE_DISABLE_EMAIL_VERIFICATION is set. Not for sensitive data.
    Roles for unverified email addresses Users with roles whose provider did not confirm their email address (email_verified = false). Check that these are the right people.
    No 2FA signal Recent logins did not contain the configured OIDC_MFA_CLAIM, so sensitive actions are blocked. Check the provider's 2FA settings and OIDC_MFA_CLAIM. (Not shown with AUTH_INSECURE_DISABLE_2FA.)
    Migration not finished OIDC_PREVIOUS_HOST is still configured after OIDC_PREVIOUS_UNTIL.

    Development mode

    AUTH_DEV_MODE lets developers run our software on their own machine without an OIDC provider, logged in as a local admin. The server refuses to start in development mode unless it only listens on localhost. Development mode is never used for servers that other people use.

    An app may let you choose the test user in development mode (for instance with a sign-in form where you type any email address, with or without a second factor), so you can try how it behaves for different users.

    For developers

    All software developed by the Societal Analytics Lab follows these rules, to ensure consistency and security across our software stack.

    Rule Details
    Same origin The server and web client are always hosted on the same domain.
    Server-side OIDC flow The server initiates and completes the OIDC flow with the trusted provider (OIDC_HOST), and sets a signed, http-only session cookie.
    Scopes The server requests the scopes openid email, nothing more. It uses sub, email, email_verified, the 2FA signal and auth_time, and no name, so users aren't asked to share more than needed.
    One session per application When AmCAT and AnnoTinder are hosted together, each application has its own session. They can share one OIDC client (the same client ID and client secret), so that users consent once per host (see One client per host). The second login completes without user interaction, while the user is still signed in at the provider.
    Own session, sign-out The application's session is independent of the provider's session: 30 minutes idle, 24 hours at most, configurable. Signing out ends it and the provider's session (see Sessions and signing out).
    Authorization on the server The server decides what users may do, not the OIDC provider (see Authorization).
    API keys for other clients Other clients (e.g. R or Python) can only access the backend via API keys.
    Email verification The server checks the email_verified claim, unless AUTH_INSECURE_DISABLE_EMAIL_VERIFICATION is set (see Weaker security).
    2FA and step-up The server checks OIDC_MFA_CLAIM and auth_time for sensitive actions, and performs step-up authentication if needed (see Two-factor authentication). AUTH_INSECURE_DISABLE_2FA drops the OIDC_MFA_CLAIM check, not the step-up.

    Sessions and signing out

    There are three kinds of session, and keeping them apart is what makes signing in and out behave as users expect:

    1. The provider's session (in Keycloak: the user session): the browser's login at the provider. While it lasts, every application of the realm can sign the user in without a password. That is useful for single sign-on (from AmCAT to AnnoTinder in one click), and a risk on a shared computer: someone who signed in to one application and only closed it leaves a login behind for all of them. So our provider keeps it short: 10 minutes without activity, at most 30 minutes.
    2. The provider's client sessions: one per application, inside the provider's session. Ordinary refresh tokens belong to them, so they stop working when the provider's session ends, including when the user signs out in any application.
    3. The application's own session: its session cookie.

    The rule: an application's session must not depend on the provider's session. Otherwise one application's sign-out, or a short provider session, would end every application's session in the middle of someone's work. So an application either:

    • keeps its own session after the login (our software: the server uses OIDC once to sign the user in, and needs no refresh token), or
    • requests offline_access: a refresh token that is independent of the provider's session (it survives a sign-out elsewhere). Tools that keep users signed in with refresh tokens (e.g. oauth2-proxy, by adding offline_access to its scopes) do it this way. In our Keycloak, a client gets it only when it asks, with the session limits of its client settings.

    How long a session lasts: an idle timeout and an absolute timeout (OWASP, Session Management), within the limits of NIST SP 800-63B-4 for logins with a second factor (at most 1 hour of inactivity, at most 24 hours in total):

    Level Without activity In total Settings
    The session 30 minutes 24 hours AUTH_SESSION_IDLE, AUTH_SESSION_MAX
    Sensitive actions (within the session) 15 minutes since the 2FA login or the last sensitive action 1 hour since the 2FA login AUTH_STEP_UP_IDLE, AUTH_STEP_UP_MAX_AGE

    An application whose use requires more may set more, and documents why: e.g. a notebook server that computes for hours while the user does nothing.

    Continuing a task without a session: an application may let one specific task continue without a login session, when the login was only needed to start it: e.g. continuing a coding job in AnnoTinder on the device where it was opened. That permission must be limited to that one task (and preferably that device), and grant nothing else. There is no general "remember me": that is what the short sessions are for.

    Signing out in an application:

    1. ends the application's own session;
    2. sends the browser to the provider's end-session endpoint, with the ID token of the login (id_token_hint, so the server keeps the ID token with the session) and a post_logout_redirect_uri. This ends the provider's session, so the next visit to any application asks for the password again.

    Other applications are not affected by a sign-out: their own sessions continue. Applications don't depend on each other's sign-out, and OIDC's back-channel logout (the provider telling every application to end its session) is not used: it would make them dependent again.

    Locking someone out (e.g. a compromised account): block them in the applications themselves (e.g. remove their role), and disable them at the provider, so they can't sign in again anywhere. Revoking their offline sessions at the provider ends the sessions of tools that use offline_access.

    The lab portal does all of this, and is a short example to follow.

    Authorization

    Authorization is based on roles. A role can be given to a specific user (IBAC), to users with a certain attribute (ABAC), or both.

    Role table

    Column Description
    role What role a user has (e.g. READ, WRITE, ADMIN).
    context The context in which the role applies (e.g. project, server).
    user_id If not null, the role is linked to a specific user (see IBAC).
    email_domain If not null, the user's verified email (email_verified = true) must have this domain (see ABAC). Can be combined with user_id to require both.
    require_email If user_id and email_domain are null: whether any user gets the role (false), or only users with a verified email address (true).
    granted_at When the role was granted (created, updated, or restored).

    Identity Based Access Control (IBAC)

    IBAC is the primary mode of authorization: roles are given to registered users.

    The identity is iss + sub, not the email address. An email address is not a unique identifier, because it can change over time: users can change email addresses, and old email addresses can be reassigned. We do use the email address as a human readable way to assign roles (e.g. giving a colleague access to a project in AmCAT). This is safe, because the role is not assigned to the email address itself, but to the user (iss + sub) that currently owns it. Changing email addresses is the responsibility of the OIDC provider: when the email for an identity has changed, the server updates the user table.

    Any user that signs in is registered, optionally with a form that collects additional information. We use this for security logs and rate limiting, which is legitimate under GDPR. Email addresses add some accountability, especially when roles require an email domain.

    User table

    Column Description
    id Unique user ID.
    email Email address of the user, from the most recent login.
    email_verified Whether the provider confirmed the email address at the most recent login: true only if it sent email_verified: true, otherwise false. NULL for shadow users. Without AUTH_INSECURE_DISABLE_EMAIL_VERIFICATION, only users with true can log in.
    has_mfa Whether the most recent login contained the 2FA signal (OIDC_MFA_CLAIM). Shown on the admin page, without a warning: 2FA is only needed for sensitive actions.
    registered_at When the user first signed in. NULL for shadow users until the account is claimed (see JIT account claiming).
    last_login_at When the user last signed in.
    reactivated_at First login after 1 year of inactivity.
    ... Optional user details (e.g. added on registration).

    Identities table

    Column Description
    user_id The user this identity belongs to.
    iss Issuer of the OIDC provider.
    sub Unique subject identifier at the OIDC provider.
    linked_at When the identity was linked to the user.
    last_login_at When the user last signed in with this identity.

    Normally a user has one identity. A user can have more than one during a migration to a new OIDC provider.

    JIT account claiming

    Just-In-Time (JIT) account claiming lets us give roles to an email address that is not yet registered. The role is given to a new shadow user, which only has an id and email (registered_at is NULL, and there is no identity yet). The current owner of the email address is invited to claim the account and role. This can be an actual invitation, or just happen automatically when they first sign in. Claiming adds an identity and sets registered_at.

    Safeguards against email reassignment

    Two safeguards prevent giving a role to a previous or future owner of an email address. A role is not given to a user if one of these conditions is true:

    Dormant users. A role is disabled when:

    role.granted_at < user.reactivated_at AND NOT user.has_mfa
    • Why: without 2FA, the OIDC provider only verifies current ownership of the email address. So after a year of inactivity, roles granted before reactivation are disabled. With 2FA required this should be rare, but it remains a safeguard for accounts claimed via email and providers that report 2FA inconsistently.
    • Restore: per role (e.g. an AmCAT project ADMIN refreshes granted_at), or by a server admin.

    Expired invitations. A role is not given when:

    user.registered_at > role.granted_at + INTERVAL '3 months'
    • Why: a role given to an unregistered email address must be claimed within 3 months, so that a future owner of the address can't claim it. Roles granted after registration are not affected, because then granted_at is later than registered_at.
    • Unclaimed invitations: a shadow user that is still unclaimed (registered_at IS NULL) has an expired invitation when now() > role.granted_at + INTERVAL '3 months'.
    • Restore: remove the invitation, or restore it by updating granted_at.

    Attribute Based Access Control (ABAC)

    ABAC is the secondary mode of authorization: roles are given based on user attributes from OIDC claims. We currently only use the email domain, because this keeps the role of the OIDC provider restricted to authentication and email verification. In the future we could include other attributes (e.g. eduPerson claims from institutional providers).

    IBAC and ABAC serve different purposes:

    IBAC ABAC
    Based on Identities, tied to specific users Attributes, properties of users that can change
    Use Users keep their roles when they change email addresses. Important for long-term projects where researchers change institutions. Give and take away access based on a user's current situation, such as their affiliation with an institution.

    Email domains are useful for:

    • Convenience: give access to anyone with an institutional email address, instead of giving everyone individual access. This should have limited privileges (never ADMIN).
    • Security: restrict access to a trusted institution. Combined with IBAC, access is restricted to a trusted person who also has a verified email address at that institution.
