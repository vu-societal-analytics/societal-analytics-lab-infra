# Installation: lab server

How the [lab server](../servers/lab.md) is set up: Caddy and the lab portal (the lab login), and how a new service is made reachable. Apps themselves are installed as on every server: [Apps on our servers](apps.md) (the system account `sal`, `/opt/<app>`, and where data goes). Why it is set up this way: [Decisions](../decisions.md#the-lab-portal-our-own-login-for-the-lab-zone-instead-of-oauth2-proxy).

Caddy and the portal run together from [deploy-lab-portal](https://github.com/vu-societal-analytics/deploy-lab-portal), in `/opt/lab-portal`. Caddy is the only thing reachable from outside: it handles HTTPS, and asks the portal who may use a service. Its configuration is generated by the portal from `services.yml`: there is no Caddyfile to edit by hand.

## 1. Caddy and the lab portal

### DNS

Two records, both pointing to this server: `lab.societal-analytics.nl` and `*.lab.societal-analytics.nl`. New services then need no DNS change. Only the lab's own services may get an address under `lab.`: see [the lab zone](../servers/lab.md#the-lab-zone-everything-under-lab).

HTTPS is automatic: every address gets a Let's Encrypt certificate, renewed on its own, as long as its DNS points to this server and ports 80 and 443 are open.

### In Keycloak

In the admin console of the `lab` realm, create the client `lab-portal`:

1. **Clients → Create client.** **Client ID:** `lab-portal`. **Name:** `Lab portal`. **Next.**
2. **Client authentication:** on. **Authentication flow:** only **Standard flow**. **Next.**
3. **Root URL** and **Home URL:** `https://lab.societal-analytics.nl`. **Valid redirect URIs:** `https://lab.societal-analytics.nl/callback` (the one place every login comes back to). **Valid post logout redirect URIs:** `https://lab.societal-analytics.nl/signed-out`. **Save.**
4. **Settings** tab, **Logout settings:** **Front channel logout** off; **Backchannel logout URL:** `https://lab.societal-analytics.nl/backchannel-logout`; **Backchannel logout session required** on. **Save.**
5. **Advanced** tab: **Proof Key for Code Exchange Code Challenge Method:** `S256`. **Save.**
6. **Credentials** tab: copy the **Client secret**.

The portal needs the `email` and `amr` claims; the `lab` realm gives them to every client ([our realm files](keycloak.md)).

### On the server

Get the deployment, as `sal`:

```bash
sudo -u sal git clone https://github.com/vu-societal-analytics/deploy-lab-portal.git /opt/lab-portal
```

```bash
cd /opt/lab-portal
```

The settings, from the examples (all three only readable by `sal`):

```bash
sudo -u sal cp .env.example .env && sudo -u sal chmod 600 .env
```

```bash
sudo -u sal cp config/services.example.yml config/services.yml
```

```bash
sudo -u sal cp config/groups.example.yml config/groups.yml
```

Then fill them in with `sudoedit -u sal`:

* **`.env`:** `OIDC_CLIENT_SECRET` (from Keycloak), `ACME_EMAIL` (for Let's Encrypt), and the SMTP settings for email to the admins (the VU mail relay, as for other apps; leave `SMTP_HOST` empty for no email). The comments in the file explain the rest.
* **`config/groups.yml`:** the lab admins (their email address in the `lab` realm). At least one.
* **`config/services.yml`:** the services ([Adding a service](#2-adding-a-service)).

The portal runs as user 1000 in its container, and writes its database, its daily copy and the Caddyfile:

```bash
sudo mkdir -p data backups && sudo chown 1000:1000 data backups caddy
```

Start it (ports 80 and 443 must be free: see [Moving from the earlier setup](#3-moving-from-the-earlier-setup) if Caddy or another web server is installed on the server itself):

```bash
sudo docker compose up -d --build
```

```bash
sudo docker compose logs -f
```

The portal logs `Caddyfile written` and `Lab portal on https://lab.societal-analytics.nl`. Then open `https://lab.societal-analytics.nl`, sign in as an admin, and check the admin page.

### Backups

`data/portal.db` holds the members, the membership requests and a log of admin actions. The portal writes a copy of it to `backups/` every day (7 kept, without sessions), which the [nightly backup](backups.md) of `/opt` picks up. Settings, `services.yml` and `groups.yml` are in `/opt/lab-portal` too.

### Updates

```bash
cd /opt/lab-portal && sudo -u sal git pull && sudo docker compose up -d --build
```

## 2. Adding a service

1. **Install the app** as described in [Apps on our servers](apps.md), with its port on `127.0.0.1`. Its address will be `<name>.lab.societal-analytics.nl`; DNS needs no change.
2. **Add it to `config/services.yml`** (`sudoedit -u sal /opt/lab-portal/config/services.yml`):

    ```yaml
    services:
      whisper:                       # the address: whisper.lab.societal-analytics.nl
        name: Whisper                # shown on the portal
        description: Transcription of audio
        upstream: 127.0.0.1:9000     # where the app listens
        access: members              # members, admins or public
        mfa: required                # only with a second factor (default: optional)
        max_upload: 2.5GB            # for large uploads
        timeout: 3000s               # for long requests
    ```

    * **No login of its own:** `access: members` (or `admins`). The service receives the user's email address in the header `X-Auth-Request-Email`.
    * **Its own login, through Keycloak:** `access: public`. Create a client for it in the `lab` realm (**Clients → Create client**, client authentication on, the app's callback URL as **Valid redirect URI**), and configure the app's OIDC settings with issuer `https://auth.societal-analytics.nl/realms/lab` (e.g. Open WebUI).
    * **An API for scripts, with the service's own API keys:** `api_bypass: [/api/*]` lets requests with an `Authorization` header on those paths skip the lab login. Only for services that check those keys themselves.
    * **Not listed on the portal:** `show: false`.

3. **Done:** the portal checks the file every minute, and Caddy reloads. If the file has an error, the previous settings stay, and `sudo docker compose logs portal` says why.

**Moving a service to its address under `lab.`:** keep the old address working for a while with a redirect in `services.yml` (its DNS must point to this server):

```yaml
redirects:
  whisper.societal-analytics.nl: https://whisper.lab.societal-analytics.nl
```

**Updating or removing an app:** see [Apps on our servers](apps.md#updating-and-removing-an-app). After removing one, also remove it from `services.yml`.

## 3. Moving from the earlier setup

The lab server first had Caddy installed on the server itself (`/etc/caddy`), with oauth2-proxy (`/opt/oauth2-proxy`) as the lab login and a static overview page. To move to the portal:

1. **Keycloak:** create the `lab-portal` client ([above](#in-keycloak)).
2. **Write `services.yml`** from the sites in `/etc/caddy/Caddyfile`: each `import authwall` site becomes a service with `access: members`; a site without it becomes `access: public`. Copy `max_size` and the timeouts, and `redir` sites to `redirects:`. A site with `authwall-group` has no equivalent yet: give it `access: admins`, or keep it out until groups are added to the portal.
3. **Set up the portal** ([above](#on-the-server)), but don't start it yet.
4. **Stop the old setup, and start the portal** (the services are briefly unreachable):

    ```bash
    sudo systemctl disable --now caddy
    ```

    ```bash
    cd /opt/oauth2-proxy && sudo docker compose down
    ```

    ```bash
    cd /opt/lab-portal && sudo docker compose up -d --build
    ```

5. **Check** every service, then add the lab's members: on the admin page (**Add a member**), or in `groups.yml` under `lab`. Until they are added, members who sign in can request membership.
6. **Clean up** after a week: `sudo apt remove caddy`, `/etc/caddy`, `/var/www/lab`, `/opt/oauth2-proxy`, and the client `lab-authwall` in Keycloak.

To go back: `sudo docker compose down` in `/opt/lab-portal`, then start the old setup again (`sudo systemctl enable --now caddy`, and `sudo docker compose up -d` in `/opt/oauth2-proxy`).

## Troubleshooting

| Problem | Likely cause |
| --- | --- |
| Keycloak shows "Invalid parameter: redirect_uri" | `https://lab.societal-analytics.nl/callback` is not in **Valid redirect URIs** of `lab-portal`, or `LAB_DOMAIN` in `.env` differs. |
| The portal logs "OIDC provider not reachable" | It can't reach `OIDC_HOST` (it keeps trying). Check the address, and that the server can reach Keycloak. |
| Caddy doesn't start: "address already in use" | Another web server uses port 80 or 443, e.g. Caddy on the server itself ([Moving from the earlier setup](#3-moving-from-the-earlier-setup)). |
| A service returns 502 | Caddy can't reach the service at its `upstream` (it must listen on `127.0.0.1:<port>` of the server), or the portal. `sudo docker compose logs caddy` says which. |
| A change to `services.yml` has no effect | The file has an error and the previous settings were kept: `sudo docker compose logs portal`. |
| The portal can't write (`EACCES`) | `data`, `backups` or `caddy` is not owned by user 1000 ([On the server](#on-the-server)). |
| A member sees "This service needs a second factor" | The service has `mfa: required`, and they signed in without a second factor. |
| No email to the admins | `SMTP_*` in `.env`; the portal logs `Email ... not sent` with the reason. |
| Admin buttons are greyed out | Admin changes need a login with a second factor from the last 10 minutes: use **Sign in again** on the admin page. |

## Tested

On a test installation (November 2026), with Keycloak 26.8 (our `lab` realm), Caddy 2.10 and the portal's Docker image, in a browser:

* a first visit to a service goes to the login, comes back through the one fixed callback, and ends on the same page; the service receives the user's email address, and forged `X-Auth-Request-*` headers are removed;
* someone without membership can request it; the admins get an email, approve it on the admin page, and the new member gets a welcome email and can use the service;
* a service with `mfa: required` refuses a login without a second factor, and explains how to add one; a service with `access: admins` refuses members; the admin page refuses members;
* admin changes need a recent second factor (an older login gets "Sign in again", which asks Keycloak for a new login);
* requests from other sites to the forms are refused (CSRF);
* signing out ends the login for all services and the Keycloak session; signing out in Keycloak ends the portal login (back-channel logout); a member removed in the portal loses access at once;
* API requests with an `Authorization` header skip the lab login only on the configured paths;
* a change to `services.yml` reaches Caddy within seconds (the generated configuration, including redirects, passes `caddy validate`); an invalid file is refused and the previous settings stay;
* the daily database copy is written and old copies are removed.
